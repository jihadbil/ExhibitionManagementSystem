# خطة إصلاح وتجهيز ExhibitionManagementSystem للإطلاق التجاري

**الإصدار:** 1.0  
**تاريخ الإعداد:** 2026-09-20  
**الفرع الجاري:** `codex/security-containment`  
**القرار الحالي:** **No-Go** للإطلاق العام أو استخدام بيانات عملاء حقيقية  
**الهدف الأول:** الوصول إلى Pilot داخلي آمن ببيانات مصطنعة  
**الهدف النهائي:** Release تجاري قابل للنشر والدعم والتدقيق والتعافي

---

## 1. نطاق الخطة

تغطي هذه الخطة المخاطر المثبتة في التدقيق الحالي:

- احتواء الأسرار وحالة النشر العام وHTTPS.
- المصادقة والصلاحيات وعزل المستأجرين وتهيئة Tenant جديد.
- سلامة الحجوزات والفواتير والمدفوعات والتذاكر وسجل التدقيق.
- التحقق من المدخلات وجودة عقود API والتوافق مع Desktop.
- الاختبارات الآلية، CI/CD، فحوص الأمن، والتوزيع الموثوق.
- إزالة البيانات الوهمية من واجهة WPF وتجهيز Installer وتحديثات العميل.
- المراقبة والنسخ الاحتياطي والاسترجاع وRunbooks.
- البريد والدفع والمستندات والخصوصية ومتطلبات Pilot والإطلاق.

لا تشمل الخطة إضافة ميزات تسويقية جديدة قبل عبور البوابة الأمنية `G1`.

## 2. خط الأساس المثبت

| العنصر | الوضع الحالي |
|---|---|
| Release build | ناجح، 0 أخطاء و0 تحذيرات |
| الاختبارات | 72/72 ناجحة بعد دفعتين من التقوية، لكنها ما زالت تحتاج اختبارات API/E2E وتزامن موسعة |
| NuGet vulnerabilities | لا توجد ثغرات معروفة وقت التدقيق |
| EF model/migrations | لا توجد تغييرات Model معلقة؛ سكربت الترحيل يتولد بنجاح |
| نشر API | ناجح |
| نشر Desktop | ناجح بعد Restore خاص بـ`win-x86`؛ غير موقع ولا يملك Auto Update |
| حالة Git | 148 تغييرًا غير ملتزم؛ الحالة الحالية غير قابلة للإصدار كمرجع ثابت |
| الإنتاج | HTTPS غير متاح من بيئة التدقيق، وHTTP لا يحول إلى HTTPS، وHealth endpoints تعيد 404 |
| الأسرار | القيم أزيلت من Working Tree، لكن آخر Commit/التاريخ يحتويان إعدادات حساسة سابقة |

### سجل التنفيذ — 2026-09-20

أُنجزت أول دفعة إصلاح داخل المستودع، مع بقاء بوابات الإصدار في حالة **No-Go** إلى أن تُستكمل الأعمال التشغيلية والاختبارات المتقدمة:

- تعريف سياسات صلاحيات مركزية وفصل `SuperAdmin` عن أعمال المستأجر التشغيلية.
- حماية وحدات الإدارة، الماليات، الرعاية، الشارات، الحجوزات، والتذاكر بسياسات متخصصة.
- تطبيق منع إعادة استخدام تذكرة الدخول، وإضافة `RowVersion` وترحيل EF لمعالجة المسح المتزامن.
- إضافة تحقق للمدخلات الحرجة في الحجوزات وخدماتها وإصدار/مسح التذاكر.
- إضافة HSTS وتقليل ترويسات كشف الخادم وتحويل Publish Profile إلى HTTPS دون حفظ كلمة المرور.
- إصلاح عميل Desktop ليرسل اتجاه المسح المدعوم `In` بدل `Entry`.
- تحويل الأدوار إلى أدوار عالمية ثابتة مع إبقاء بيانات الربط القديمة مؤقتًا للترحيل والرجوع الآمن.
- تنفيذ تهيئة Tenant ذرية: المستأجر + اشتراك Trial + دعوة أول مدير + Audit.
- تخزين Hash الدعوة فقط، ومنع الدعوات النشطة المكررة، ودعم الانتهاء والإلغاء وإعادة الإرسال والاستخدام مرة واحدة.
- إضافة إرسال SMTP وصفحة HTTPS لقبول الدعوة وإنشاء أول `TenantAdmin`.
- اختبار ترقية Migration والرجوع عنها ثم تطبيقها مجددًا على SQL Server LocalDB بنجاح.
- البناء Release ناجح بلا تحذيرات أو أخطاء، و72/72 اختبارًا ناجحًا، ولا توجد تغييرات EF معلقة.

الأعمال الخارجية غير المنجزة: تدوير الأسرار، تنظيف تاريخ Git، إعداد شهادة وربط HTTPS على المضيف، وإبطال الجلسات الحالية. كما لم تُنفذ بعد اختبارات التزامن على SQL Server الحقيقي أو اختبارات 401/403 التكاملية لكل Endpoint.

### `REL-P0-003` إصلاح HTTPS والنشر الحالي

**الملفات المتوقعة:**

- `ExhibitionManagementSystem/Properties/PublishProfiles/site81870-WebDeploy.pubxml`

**معيار القبول:** TLS ناجح، HTTP يعيد Redirect دائمًا، وReadiness يعكس اتصال DB دون كشف أسرار.

### `REL-P0-004` إنشاء Release baseline قابل لإعادة البناء

## 6. المرحلة الأولى — الهوية والصلاحيات وتعدد المستأجرين

**الأولوية:** P0/P1  
**المدة المستهدفة:** 5–8 أيام عمل  
**المالك:** Backend + Security reviewer

### `IAM-101` اعتماد مصفوفة Permissions

الأدوار الأولية:

| الدور | النطاق المسموح |
|---|---|
| SuperAdmin | إدارة المنصة والمستأجرين فقط |
| TenantAdmin | إدارة مستخدمي وبيانات Tenant الخاص به |
| EventManager | المعارض والقاعات والأجنحة والحجوزات |
| Finance | الفواتير والمدفوعات والتقارير المالية |
| GateOperator | مسح التذاكر فقط |
| Exhibitor | بياناته وحجوزاته وفواتيره فقط |
| Viewer/Auditor | قراءة محدودة بلا تعديل |

المهام:

- تعريف Permission constants وسياسات Authorization.
- استبدال `AdminOnly` في العمليات المتخصصة بسياسة Permission مناسبة.
- حماية كل عمليات الكتابة في Sponsorship وBadges وTickets.
- منع SuperAdmin من العمل داخل Tenant كموظف عادي دون Impersonation مؤقت ومدقق.
- إنشاء مصفوفة Endpoint -> Permission موثقة.

**اختبارات القبول:** لكل Endpoint حساس توجد اختبارات 401 و403 ونجاح للدور الصحيح.

### `IAM-102` إصلاح تصميم الأدوار متعددة المستأجرين

**حالة التنفيذ:** مكتمل داخل الكود والترحيل؛ بانتظار تحقق Staging واختبارات API التكاملية.

يجب اختيار أحد تصميمين قبل التنفيذ:

1. أدوار عالمية ثابتة، بينما العضوية والصلاحية مقيدتان بسياق Tenant.
2. أدوار منفصلة لكل Tenant مع فهرس مركب `(TenantID, NormalizedName)` وRoleStore واعٍ بالمستأجر.

الخيار الموصى به للمشروع الحالي: **أدوار عالمية ثابتة + Permissions ثابتة + Tenant membership موثوق**؛ يقلل تعقيد ASP.NET Identity ويمنع تعارض أسماء الأدوار.

**معيار القبول:** يمكن إنشاء Tenantين واستخدام الدور نفسه دون تعارض أو إسناد دور من Tenant آخر.

### `IAM-103` Tenant provisioning وBootstrap آمن

**حالة التنفيذ:** مكتمل داخل الكود والترحيل، بما في ذلك SMTP وصفحة قبول الدعوة؛ بانتظار ضبط SMTP وتجربة Staging الفعلية.

- جعل إنشاء Tenant معاملة ذرية تنشئ إعداداته الأساسية واشتراك Trial عند الحاجة.
- إنشاء دعوة أحادية الاستخدام لأول TenantAdmin بدل كلمة مرور ثابتة.
- انتهاء الدعوة خلال مدة قصيرة وتخزين Hash فقط.
- إضافة شاشة/مسار لإعادة إرسال الدعوة وإلغائها.
- تسجيل إنشاء Tenant والدعوة وقبولها في Audit.

**معيار القبول:** دورة آلية كاملة: SuperAdmin ينشئ Tenant -> تصل دعوة -> أول مدير يضبط كلمة المرور -> يسجل الدخول ضمن Tenant الصحيح.

### `IAM-104` استعادة كلمة المرور

- دمج واجهة `IEmailSender` مع مزود Production قابل للاستبدال.
- إرسال رابط HTTPS أحادي الاستخدام قصير الصلاحية.
- عدم إعادة Token في API أو Logs.
- توحيد الاستجابة لمنع تعداد الحسابات في request وconfirm.
- إبطال الجلسات بعد نجاح إعادة التعيين.
- قوالب عربية وإنجليزية واختبارات Expiry/Reuse.

### `IAM-105` تقوية الجلسات

- إضافة Session ID/Device ID واضح وإلغاء جلسة واحدة أو جميع الأجهزة.
- تحديد حد أقصى للجلسات النشطة للمستخدم.
- إضافة Cleanup دوري للجلسات وIdempotency records المنتهية.
- دراسة MFA الإلزامي لـSuperAdmin وTenantAdmin.

**بوابة الخروج:** `G1`، بعد Security review وصفر P0/P1 أمني.

## 7. المرحلة الثانية — سلامة البيانات والمنطق التشغيلي

**الأولوية:** P1  
**المدة المستهدفة:** 5–8 أيام عمل  
**المالك:** Backend + DBA/QA

### `DATA-201` منع Ticket replay

- تعريف State Machine واضحة: Active -> Inside -> Outside/Used -> Cancelled/Expired.
- رفض `In` متكرر دون `Out` عندما تمنع سياسة التذكرة إعادة الدخول.
- دعم سياسة Re-entry لكل نوع تذكرة.
- إضافة RowVersion أو قيد ذري يمنع نجاح مسحين متزامنين للتذكرة نفسها.
- تسجيل البوابة والجهاز والمستخدم والنتيجة والسبب.
- تصميم Offline gate sync مع Conflict policy قبل الإطلاق الميداني.

**اختبارات القبول:** 20 طلب Scan متزامن لنفس التذكرة؛ نجاح واحد فقط عندما لا يسمح بإعادة الدخول.

### `DATA-202` إكمال Validation وقيود DB

- إضافة حدود موجبة للمساحات والأسعار والكميات والضرائب.
- اشتراط اختيار Booth أو Merge واحد فقط وفق قاعدة المجال.
- منع تواريخ نهاية قبل البداية وتواريخ صلاحية غير منطقية.
- وضع أطوال قصوى لكل النصوص والـJSON والروابط والملاحظات.
- إضافة Check Constraints في DB للقيم المالية الحرجة.
- رفض حقول `TenantID` القادمة من DTOs العامة أو حذفها منها.
- إزالة علاقات EF الظلية المكتشفة (`ExhibitionID1` و`ExhibitorID1` و`InvoiceID1` و`VisitorID1`) وتثبيت العلاقات صراحةً قبل أي ترحيل إنتاجي.

### `DATA-203` جعل Audit ذريًا وكاملًا

- حفظ بيانات العملية وAudit entries داخل Transaction واحدة.
- ضمان Rollback للبيانات إذا فشل تسجيل التدقيق في العمليات التي تتطلب Audit إلزاميًا.
- تسجيل تغييرات المستخدمين والأدوار والجلسات وImpersonation.
- منع Audit من تخزين PII/Token/Password/Connection string.
- إضافة سياسة احتفاظ ووصول للسجل.

### `DATA-204` اختبارات الحجز والدفع المتزامن

- تشغيل الاختبارات على SQL Server حقيقي، وليس EF InMemory.
- 20–100 طلب حجز لنفس Booth/Merge؛ نجاح واحد فقط.
- دفعات متزامنة على الرصيد المتبقي؛ لا Overpayment.
- إصدار فواتير متزامن؛ لا أرقام مكررة.
- إعادة الطلب نفسه بنفس Idempotency-Key وإعادة النتيجة دون تكرار الأثر.
- نفس المفتاح مع Body مختلف يعيد 409.

### `DATA-205` قواعد الماليات القانونية

- تحديد سياسة التقريب وعدد المنازل لكل عملة.
- تثبيت سعر الصرف داخل الحجز والفاتورة ومنع تعديله تاريخيًا.
- إعداد الضريبة لكل Tenant/بلد بدل قيم عامة.
- منع تعديل الفاتورة الصادرة أو المدفوعة من جميع المسارات.
- مراجعة حالات Partial/Overdue/Cancelled/Refunded وCredit Note.
- إضافة Snapshot لبيانات البائع والعميل والرقم الضريبي.

**بوابة الخروج:** `G2`.

## 8. المرحلة الثالثة — API والاختبارات وCI/CD

**الأولوية:** P1  
**المدة المستهدفة:** 5–8 أيام عمل  
**المالك:** Backend + QA Automation + DevOps

### `QA-301` هيكلة الاختبارات

- `Domain.UnitTests`: الأسعار والحالات والحسابات.
- `Services.UnitTests`: قواعد الخدمات والصلاحيات.
- `Infrastructure.IntegrationTests`: SQL Server حقيقي والترحيلات.
- `Api.IntegrationTests`: `WebApplicationFactory` وعقود HTTP الكاملة.
- `Desktop.Tests`: ViewModels وApiClients وتجديد الجلسة.
- `EndToEnd.Tests`: Tenant -> معرض -> جناح -> حجز -> فاتورة -> دفع -> تذكرة -> Scan -> تقرير.

**الهدف:** تغطية سيناريوهات المسارات الحرجة 100%، وحد استرشادي 80% لخدمات الأمن والماليات.

### `API-302` Versioning والعقود

- اعتماد `/api/v1` أو Header versioning.
- نشر OpenAPI artifact من CI.
- Contract tests بين API وDesktop.
- Breaking-change detection قبل الدمج.
- توحيد ProblemDetails لكل أخطاء Validation والمجال.

### `CI-303` تقوية Pipeline

- تفعيل TreatWarningsAsErrors في CI تدريجيًا.
- CodeQL/SAST وGitleaks كامل التاريخ.
- SBOM وLicense scan وDependabot/Renovate.
- NuGet lock files أو Central Package Management.
- إزالة الحزم غير المستخدمة مثل Microsoft.Identity.Web إذا لم يعتمد المشروع OIDC.
- إزالة `NoWarn=NU1605` بعد حل سبب التحذير بدل حجبه.
- تحديث xUnit القديم أو الانتقال المدروس إلى xUnit v3.
- شراء ترخيص AutoMapper 16 للإنتاج أو استبداله بمحوّل مفتوح قبل Pilot؛ لا يجوز الرجوع إلى AutoMapper 14 بسبب الثغرة عالية الخطورة `GHSA-rvv3-g6hj-g44x`.
- توقيع Artifacts وإضافة checksums وprovenance.

### `PERF-304` اختبارات الحمل

- تسجيل الدخول وتجديد Token.
- تسجيل زوار جماعي.
- حجز متزامن.
- مسح تذاكر عند عدة بوابات.
- تقارير على بيانات كبيرة.
- Soak test لمدة 8 ساعات على الأقل.

**بوابة الخروج:** `G3` بعد نجاح CI الإلزامي وعدم وجود Flaky tests.

- إزالة Revenue fallback والتوزيع الوهمي.
- استبدال Mock traffic ببيانات Scan مجمعة من API، أو إظهار حالة "لا توجد بيانات".
- وسم Preview data بوضوح داخل مصمم الشارة فقط.

### `DESK-402` الاعتمادية والأخطاء

- Global dispatcher/task exception handling مع Crash ID وRedaction.
- حالات موحدة: Loading وEmpty وError وOffline.
- منع النقر المكرر للحجز والدفع والمسح.
- سياسة Retry للقراءات فقط، وعدم إعادة الكتابة دون Idempotency.
- عرض إصدار Desktop وAPI compatibility وحالة الاتصال في Diagnostics.

### `DESK-403` التوزيع والتحديث

- الانتقال إلى `win-x64` كافتراضي؛ دعم x86 فقط عند وجود متطلب أجهزة مثبت.
- إنشاء MSIX أو Installer مناسب وموقع رقميًا.
- Stable/Beta channels وتحديث تلقائي مع Rollback.
- عدم حفظ Refresh Token على القرص إلا عبر DPAPI/Credential Manager إذا تقرر Remember me.
- اختبار DPI 125–200% وRTL ولوحة المفاتيح وقارئ الشاشة.
- اختبار الطابعات والماسحات الفعلية المستهدفة.

## 10. المرحلة الخامسة — التشغيل والتعافي

**الأولوية:** P1  
**المدة المستهدفة:** 5–8 أيام عمل  
**المالك:** DevOps/SRE

### `OPS-501` Observability

- Structured logs مع Correlation ID وTenant ID وRedaction.
- Metrics لمعدل الطلبات و5xx وp95 وتعارض الحجز والدفع ومسح التذاكر.
- Tracing للعمليات الحرجة.
- Alerts للـReadiness، معدل الأخطاء، فشل Login، وDB saturation.
- Dashboard تشغيلي منفصل عن Dashboard المنتج.

### `OPS-502` Backup وRestore

- نسخ مشفر مع Point-in-Time Recovery إن كانت المنصة تدعمه.
- فصل صلاحيات النسخ عن حساب التطبيق.
- Restore فعلي إلى بيئة منفصلة والتحقق من سلامة البيانات.
- أهداف Pilot: `RPO <= 15 دقيقة` و`RTO <= ساعتين`.

### `OPS-503` نشر وترحيلات آمنة

- Staging مطابق للإنتاج قدر الإمكان.
- Pipeline: Backup -> Migration preflight -> Migrate -> Smoke tests -> Traffic enable.
- Roll-forward وRollback موثقان ومختبران.
- نشر Blue/Green أو Rolling إذا سمحت الاستضافة.
- منع تطبيق Migration تلقائيًا عند بدء Web App.

### `OPS-504` Runbooks

- تسريب سر أو Token.
- تعطل قاعدة البيانات.
- Migration فاشل.
- نشر فاشل/عودة لإصدار سابق.
- انقطاع الإنترنت أثناء المعرض.
- فشل البريد أو بوابة الدفع.

**بوابة الخروج:** `G4`.

## 13. Definition of Done

لا تعتبر أي مهمة مكتملة إلا عند تحقق الآتي:

- الكود داخل Branch/PR ومراجع من شخص آخر.
- Unit/Integration/Security regression tests ناجحة.
- لا أسرار أو PII حساسة في الشفرة أو Logs أو Artifacts.
- أخطاء المجال مربوطة بحالة HTTP ورسالة مستخدم مناسبة.
- Migration مرفقة ومختبرة على قاعدة جديدة وترقية قاعدة سابقة عند تغير Schema.
- الوثائق وOpenAPI وRunbook محدثة عند الحاجة.
- Telemetry/Alert موجودان للعمليات التشغيلية الجديدة.
- لا TODO أو Mock أو Feature غير مكتملة في المسار الإنتاجي دون Feature Flag وتذكرة ومالك وموعد.
- معيار القبول موثق بأمر اختبار أو دليل تشغيل قابل لإعادة التنفيذ.
